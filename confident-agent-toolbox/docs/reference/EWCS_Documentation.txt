================================================================================
1. PURPOSE AND SCOPE
================================================================================

The EWCS (Evidence-Weighted Confidence Score) is the primary quantitative
metric for the Confident Agent. It aggregates the verdicts of six independent
verification layers into a single confidence value between 0 and 1, plus a
diagnostic signed score between -1 and 1.

The EWCS answers the question:

    "How much of the applicable verification weight is supported by
     positive evidence?"

It does NOT answer:

    "What should we do with this code?"

That is the DecisionPolicy's job. The EWCS produces evidence. The policy
interprets it. This separation is deliberate and is discussed in Section 7.

Scope of this document:

    - The EWCS class
    - Its two companion data classes (LayerContribution, EWCSReport)
    - The three canonical constants it depends on
    - The schema types it consumes
    - The tests that verify its behaviour

Out of scope:

    - DecisionPolicy (separate document)
    - The six layer verifiers (separate documents)
    - The ClaimExtractor (separate document)
    - The orchestration flow (separate document)


================================================================================
2. POSITION IN THE TOOL
================================================================================

The EWCS sits between the verification layers and the decision policy:

    ┌─────────────────────────────────────────────────────────────┐
    │                    Six Verification Layers                  │
    │                                                             │
    │   LayerOne    LayerTwo    LayerThree    LayerFour          │
    │   LayerFive   LayerSix                                      │
    │                                                             │
    │   Each layer evaluates multiple claims internally,          │
    │   then returns exactly ONE aggregated LayerResult.          │
    └──────────────────────────┬──────────────────────────────────┘
                               │
                               │  [LayerResult × 6]
                               ▼
    ┌─────────────────────────────────────────────────────────────┐
    │                          EWCS                               │
    │                                                             │
    │   1. record(result) for each of the six layers              │
    │   2. finalise() computes the score and returns a report     │
    └──────────────────────────┬──────────────────────────────────┘
                               │
                               │  EWCSReport
                               ▼
    ┌─────────────────────────────────────────────────────────────┐
    │                     DecisionPolicy                          │
    │                                                             │
    │   Applies safety constraint, then confidence thresholds.    │
    │   Returns a DecisionSignal.                                 │
    └─────────────────────────────────────────────────────────────┘

The EWCS is a pure accumulator. It receives six results and returns one
report. It does not verify, correct, decide, or persist anything.

The EWCS has no knowledge of:

    - The code being verified
    - The claims extracted from the code
    - The evidence sources used by the layers
    - The thresholds used by the decision policy
    - The experiment the tool is being used in


================================================================================
3. DEPENDENCIES
================================================================================

The EWCS imports four names from confident_agent.schemas. Each is defined
below with its purpose and contract.

--------------------------------------------------------------------------------
3.1  schemas.py — LayerName
--------------------------------------------------------------------------------

LayerName is a str-Enum identifying the six verification layers.

    class LayerName(str, Enum):
        INTERFACE       = "interface"
        IDENTIFIER      = "identifier"
        ACCESS_POINT    = "access_point"
        INPUT_CONTRACT  = "input_contract"
        OUTPUT_CONTRACT = "output_contract"
        CONTEXTUAL      = "contextual"

Why str-Enum?

    - JSON-serialisable without a custom encoder
    - Hashing works like a string (usable as dict keys)
    - Log-friendly (prints the value, not the repr)
    - Type-safe (typos raise at import time, not runtime)

Why exactly these six?

    The six names correspond to the six verification layers defined in the
    project design. Each represents one question the tool asks about the
    code. The names are stable; the layer classes and weights depend on
    them.

--------------------------------------------------------------------------------
3.2  schemas.py — VerificationState
--------------------------------------------------------------------------------

VerificationState is a str-Enum of the four possible outcomes for a layer.

    class VerificationState(str, Enum):
        VERIFIED_CORRECT   = "verified_correct"
        VERIFIED_INCORRECT = "verified_incorrect"
        UNVERIFIABLE       = "unverifiable"
        NOT_APPLICABLE     = "not_applicable"

Semantics:

    VERIFIED_CORRECT
        Evidence supports the claim. Contributes positively to the EWCS.

    VERIFIED_INCORRECT
        Evidence contradicts the claim. Contributes zero to the positive
        numerator and negatively to the signed score. Also triggers the
        decision policy's safety constraint.

    UNVERIFIABLE
        The layer ran but could not establish whether the claim is
        correct. Contributes zero to the numerator but retains its
        weight in the denominator. This pulls the score down.

    NOT_APPLICABLE
        The layer had nothing to verify for this task (e.g., no
        authentication was used, so LayerSix had nothing to check).
        Excluded entirely from numerator and denominator.

The critical distinction is between UNVERIFIABLE and NOT_APPLICABLE:

    UNVERIFIABLE   = "we tried, we could not tell"     → counts against us
    NOT_APPLICABLE = "there was nothing to try"        → excluded

Collapsing these two into a single state would either under-penalise
unverifiable claims or over-penalise tasks with no applicable evidence.

--------------------------------------------------------------------------------
3.3  schemas.py — EvidenceTier
--------------------------------------------------------------------------------

EvidenceTier is a str-Enum describing how strong the evidence is.

    class EvidenceTier(str, Enum):
        TIER_1 = "tier_1"    # authoritative (discovered OpenAPI spec)
        TIER_2 = "tier_2"    # strong (PyPI metadata)
        TIER_3 = "tier_3"    # empirical (runtime execution — reserved)
        TIER_4 = "tier_4"    # supporting (Pyright diagnostics)
        NONE   = "none"      # no evidence

Why an enum and not a float?

    The tier is a categorical fact about the evidence source. The mapping
    from tier to a numeric factor is a design choice, owned by the EWCS
    (see DEFAULT_TIER_FACTORS). Keeping them separate means the numeric
    weighting can be revisited during sensitivity analysis without
    touching the schema.

Why is TIER_3 reserved?

    TIER_3 corresponds to runtime execution. The tool never executes
    LLM-generated code, so TIER_3 is reserved for future work. It is
    present in the enum to make the hierarchy complete.

--------------------------------------------------------------------------------
3.4  schemas.py — LayerResult
--------------------------------------------------------------------------------

LayerResult is the aggregated verdict from one verifier.

    @dataclass(frozen=True)
    class LayerResult:
        layer: LayerName
        state: VerificationState
        tier: EvidenceTier
        weight: int
        evidence_source: str
        evidence_detail: str
        hallucination_type: Optional[HallucinationCode] = None
        claim_ids: tuple[str, ...] = ()

Field-by-field:

    layer
        Which layer produced this result. Used as the dict key by EWCS
        and as the disambiguator when validating against LAYER_WEIGHTS.

    state
        The verdict. One of the four VerificationState values.

    tier
        The strongest evidence tier that supported the state. If the
        state is VERIFIED_INCORRECT, this is the tier of the evidence
        that contradicted the claim.

    weight
        The layer's declared weight. This field is retained in the
        schema for compatibility and for the verifier's own use. EWCS
        does not trust it — see Section 7.2.

    evidence_source
        Human-readable string. Examples: "PyPI", "OpenAPI spec",
        "Pyright", "Metadata". Not parsed by EWCS; used only in
        human-readable output and in tests.

    evidence_detail
        Human-readable explanation. Examples: "requests==2.32.0 exists
        on PyPI", "Endpoint /user/1 not found in spec".

    hallucination_type
        Optional H-code (H01–H10). Present only when state is
        VERIFIED_INCORRECT. None otherwise.

    claim_ids
        Tuple of claim_id values this aggregate covers. Optional. Allows
        the orchestrator or downstream tooling to trace which specific
        claims contributed to the layer's verdict.

Why frozen?

    LayerResult is a value object. Once a verifier has produced it, no
    part of the system should mutate it. Freezing prevents accidental
    modification in the orchestrator or in tests.

Why is weight in the schema at all, if EWCS ignores it?

    Layer classes own their own weight declaration. Removing the field
    would require changing every layer class, which would block the
    EWCS work. Keeping it allows layers to declare their weight while
    EWCS uses its canonical source. See Section 7.2 for the full
    rationale.


================================================================================
4. CANONICAL DEFINITIONS
================================================================================

These three constants live at the top of ewcs.py and are the single source
of truth for the EWCS computation.

--------------------------------------------------------------------------------
4.1  LAYER_WEIGHTS
--------------------------------------------------------------------------------

    LAYER_WEIGHTS: dict[LayerName, int] = {
        LayerName.INTERFACE:       3,
        LayerName.IDENTIFIER:      3,
        LayerName.ACCESS_POINT:    4,
        LayerName.INPUT_CONTRACT:  2,
        LayerName.OUTPUT_CONTRACT: 1,
        LayerName.CONTEXTUAL:      2,
    }

The relative importance of each layer.

    ACCESS_POINT (4) is heaviest: a wrong endpoint is the most severe
    API hallucination because the call cannot succeed.

    INTERFACE and IDENTIFIER (3 each): a non-existent library or method
    is equally fatal — the code cannot even import.

    INPUT_CONTRACT and CONTEXTUAL (2 each): invalid parameters or wrong
    auth are serious but often produce a clearer runtime error.

    OUTPUT_CONTRACT (1) is lightest: a wrong response field is a
    downstream bug, not a call failure.

Total weight: 15.

These are research design choices, not empirical constants. The report
must include a sensitivity analysis across at least five weighting
schemes. LAYER_WEIGHTS is the Scheme A ("proposed") definition.

EWCS validates every incoming LayerResult's weight against this dict
and raises ValueError on mismatch. This ensures the score cannot
silently drift if a layer class declares the wrong weight.

--------------------------------------------------------------------------------
4.2  EXPECTED_LAYERS
--------------------------------------------------------------------------------

    EXPECTED_LAYERS: tuple[LayerName, ...] = tuple(LAYER_WEIGHTS.keys())

A derived tuple, in canonical order (INTERFACE, IDENTIFIER, ACCESS_POINT,
INPUT_CONTRACT, OUTPUT_CONTRACT, CONTEXTUAL).

Used for two purposes:

    1. Iterating contributions in deterministic order in the report.
    2. Determining which layers are missing at finalise time.

Derived from LAYER_WEIGHTS so the two cannot go out of sync.

--------------------------------------------------------------------------------
4.3  DEFAULT_TIER_FACTORS
--------------------------------------------------------------------------------

    DEFAULT_TIER_FACTORS: dict[EvidenceTier, float] = {
        EvidenceTier.TIER_1: 1.00,
        EvidenceTier.TIER_2: 0.80,
        EvidenceTier.TIER_3: 0.90,
        EvidenceTier.TIER_4: 0.50,
        EvidenceTier.NONE:   0.00,
    }

The confidence multiplier applied to a layer's weight when the layer is
VERIFIED_CORRECT.

Why TIER_3 = 0.90 sits between TIER_1 and TIER_2?

    Runtime execution (TIER_3) is reserved. If it were ever used, it
    would be slightly weaker than an authoritative spec but stronger
    than metadata — because the code actually ran and returned
    something. This is a placeholder; the tool never uses TIER_3.

Why TIER_4 = 0.50?

    Pyright diagnostics are strong signals of incorrectness but produce
    false positives on dynamic code. A factor of 0.5 means a Tier 4
    correct verdict contributes half of a layer's weight.

    In the worked example below, this distinction is what makes the
    difference between an EWCS of 0.80 (if all evidence were Tier 1)
    and 0.4923 (the actual value).

Why NONE = 0.00?

    No evidence means no credit. A VERIFIED_CORRECT result with
    tier=NONE would contribute nothing; in practice no verifier
    produces such a result, and missing layers are filled as
    UNVERIFIABLE (which contributes 0 regardless of tier).


================================================================================
5. THE THREE CLASSES
================================================================================

--------------------------------------------------------------------------------
5.1  LayerContribution
--------------------------------------------------------------------------------

    @dataclass(frozen=True)
    class LayerContribution:
        layer: LayerName
        state: VerificationState
        tier: EvidenceTier
        weight: int
        tier_factor: float
        positive_contribution: float
        signed_contribution: float

Purpose:

    A single, pre-computed row in the final report. It is a *view* of
    one layer's result after the canonical weight and tier factor have
    been applied. It exists so the report can present the arithmetic
    transparently — a reader can verify the EWCS by summing the
    positive_contribution column and dividing by the sum of the weight
    column.

Why frozen?

    The report is immutable. Every component of it must be immutable
    too. A frozen LayerContribution cannot be mutated after the fact.

Why not just store the LayerResult in the report?

    LayerResult carries raw inputs. LayerContribution carries the
    derived values after the formula has been applied. Keeping them
    separate makes the report self-documenting: no arithmetic is
    required to interpret a contribution.

Field semantics:

    weight
        The canonical weight applied. For reported layers this is
        LAYER_WEIGHTS[layer]. For missing layers this is 0.

    tier_factor
        The factor from DEFAULT_TIER_FACTORS[tier].

    positive_contribution
        weight × tier_factor when state == VERIFIED_CORRECT, else 0.
        This is the value that sums to the numerator of the EWCS.

    signed_contribution
        +weight × tier_factor when CORRECT
        −weight × tier_factor when INCORRECT
         0                        when UNVERIFIABLE or NOT_APPLICABLE
        This is the value that sums to the numerator of the signed score.

--------------------------------------------------------------------------------
5.2  EWCSReport
--------------------------------------------------------------------------------

    @dataclass(frozen=True)
    class EWCSReport:
        task_id: str
        ewcs: float
        signed_score: float
        has_incorrect_layer: bool
        total_applicable_weight: int
        positive_weight: float
        contributions: tuple[LayerContribution, ...]
        missing_layers: tuple[LayerName, ...]

Purpose:

    The final, immutable output of the EWCS computation.

Why frozen?

    The report is the artefact that flows into the DecisionPolicy and,
    ultimately, into the VerificationReport that is returned to the
    caller. It must not be mutable after construction. frozen=True
    prevents reassignment of top-level fields.

    Frozen is not transitive. The contributions field is a tuple, not a
    list, so the nested sequence is also immutable. Each LayerContribution
    is itself frozen. This gives full immutability from the report down.

Why tuples and not lists?

    Lists are mutable. Storing a list in a frozen dataclass gives a
    false sense of immutability — the field cannot be reassigned but
    the list contents can still be appended to or replaced in place.

    Tuples are immutable. A tuple of frozen dataclasses is fully
    immutable, all the way down.

Field-by-field:

    task_id
        The task identifier passed to EWCS.__init__. Carried through so
        downstream consumers can correlate the report with the task.

    ewcs
        The Evidence-Weighted Confidence Score in [0, 1]. Rounded to
        four decimal places to avoid float noise in comparisons and
        logging.

    signed_score
        The diagnostic signed score in [-1, 1]. Rounded to four places.

    has_incorrect_layer
        True if any layer reported VERIFIED_INCORRECT. This is the flag
        the DecisionPolicy reads first, before considering the numeric
        score. See Section 7.

    total_applicable_weight
        The denominator of the EWCS formula. Exposed so the report is
        self-auditable.

    positive_weight
        The numerator of the EWCS formula. Exposed for the same reason.

    contributions
        One LayerContribution per expected layer, in canonical order.
        Includes missing layers (with weight 0) for full transparency.

    missing_layers
        The subset of expected layers that did not report. Empty if the
        EWCS received all six. Non-empty means the score was computed
        on partial evidence.

Why is missing_layers separate from contributions?

    A reader can determine missing layers by inspecting contributions
    (weight 0, state UNVERIFIABLE, source "none"). But that requires
    iterating. missing_layers makes the fact directly accessible:

        if report.missing_layers:
            log.warning("Partial verification: %s", report.missing_layers)

    This is a five-character check instead of a loop. For downstream
    tooling and diagnostics, the direct field is worth the small
    redundancy.

--------------------------------------------------------------------------------
5.3  EWCS
--------------------------------------------------------------------------------

    class EWCS:
        def __init__(self, task_id: str) -> None: ...
        def record(self, result: LayerResult) -> None: ...
        def finalise(self) -> EWCSReport: ...
        @property
        def is_complete(self) -> bool: ...

Purpose:

    The accumulator. Receives LayerResult objects one at a time, stores
    them, and on request computes an EWCSReport.

Public API — three members:

    __init__(task_id)
        Creates an empty accumulator. Takes only the task identifier.
        No configuration. No tier factors. No weight overrides. See
        Section 7.6 for why.

    record(result)
        Adds one LayerResult. Order-independent. Raises on duplicate
        layer, on post-finalise calls, or on weight mismatch.

    finalise()
        Computes and returns the report. Idempotent — repeated calls
        return the same object.

    is_complete
        A derived property. True after finalise() has been called. Not
        a settable field.

Internal state:

    _task_id: str
    _results: dict[LayerName, LayerResult]
    _finalised: Optional[EWCSReport]
    _lock: threading.Lock

There is no other state. In particular, there is no separate
"completeness" flag — completeness is derived from whether _finalised
has been populated. See Section 7.3 for the rationale.


================================================================================
6. THE FORMULA
================================================================================

--------------------------------------------------------------------------------
6.1  EWCS
--------------------------------------------------------------------------------

                      Σ (w_l × tier_factor_l)
    EWCS = ─────────────────────────────────────────
                      Σ (w_l)

    Numerator:   over layers where state == VERIFIED_CORRECT
    Denominator: over all layers where state != NOT_APPLICABLE

Interpretation:

    EWCS = 1.0
        Every applicable layer's full weight is backed by Tier 1
        positive evidence. Maximum confidence.

    EWCS = 0.5
        Half of the applicable weight is supported by positive evidence,
        at whatever tier factors applied.

    EWCS = 0.0
        No layer produced positive evidence. Either all layers are
        UNVERIFIABLE or all layers reported zero-weight contributions.

The EWCS is NOT a probability. A value of 0.85 does not mean "85%
chance the code is correct." It means "85% of the applicable
verification weight is supported by positive evidence at the recorded
evidence tiers."

--------------------------------------------------------------------------------
6.2  Signed Score
--------------------------------------------------------------------------------

                      Σ (w_l × s_l)
    signed = ─────────────────────────────
                      Σ (w_l)

    s_l = +tier_factor   when state == VERIFIED_CORRECT
    s_l = −tier_factor   when state == VERIFIED_INCORRECT
    s_l =  0             when state == UNVERIFIABLE or NOT_APPLICABLE

Interpretation:

    signed = +1.0
        All layers correct at Tier 1. Same as EWCS = 1.0.

    signed = 0.0
        Positive and negative evidence cancel, or no evidence at all.

    signed = −1.0
        All layers incorrect at Tier 1.

Purpose:

    The signed score is diagnostic only. It is never used for a
    decision. It provides a single value that captures both the
    magnitude and direction of the evidence — useful in the
    experimental analysis when comparing distributions between
    baseline and intervention.

Why not use signed_score as the primary metric?

    Because the DecisionPolicy treats VERIFIED_INCORRECT categorically,
    not numerically. A single incorrect layer forces CORRECT regardless
    of the signed score. The EWCS is the primary metric because it
    measures the strength of positive evidence, which is what the
    thresholds are calibrated against.

--------------------------------------------------------------------------------
6.3  Worked Example
--------------------------------------------------------------------------------

Task: fetch a user by ID from JSONPlaceholder.

The LLM generated code that calls /user/{user_id} — but the correct
path is /users/{user_id}. Layer 3 detects this. The other layers pass.

Layer results recorded:

    INTERFACE       VERIFIED_CORRECT   Tier 2   (PyPI, weight 3)
    IDENTIFIER      VERIFIED_CORRECT   Tier 4   (Pyright, weight 3)
    ACCESS_POINT    VERIFIED_INCORRECT Tier 1   (OpenAPI, weight 4)
    INPUT_CONTRACT  VERIFIED_CORRECT   Tier 1   (OpenAPI, weight 2)
    OUTPUT_CONTRACT VERIFIED_CORRECT   Tier 4   (Pyright, weight 1)
    CONTEXTUAL      NOT_APPLICABLE     NONE     (excluded)

Contribution table:

    Layer             Weight  State               Tier    Factor  Positive  Signed
    ----------------  ------  ------------------  ------  ------  --------  --------
    INTERFACE              3  VERIFIED_CORRECT    Tier 2    0.80      2.40     +2.40
    IDENTIFIER             3  VERIFIED_CORRECT    Tier 4    0.50      1.50     +1.50
    ACCESS_POINT           4  VERIFIED_INCORRECT  Tier 1    1.00      0.00     -4.00
    INPUT_CONTRACT         2  VERIFIED_CORRECT    Tier 1    1.00      2.00     +2.00
    OUTPUT_CONTRACT        1  VERIFIED_CORRECT    Tier 4    0.50      0.50     +0.50
    CONTEXTUAL             0  NOT_APPLICABLE      NONE      0.00      0.00      0.00
    ----------------  ------                      TOTAL            --------  --------
    (applicable only)     13                                      6.40     +2.40

EWCS calculation:

    positive_weight = 2.40 + 1.50 + 0.00 + 2.00 + 0.50 = 6.40
    total_weight    = 3 + 3 + 4 + 2 + 1               = 13

    EWCS = 6.40 / 13 = 0.4923

Signed score calculation:

    signed_weight = 2.40 + 1.50 − 4.00 + 2.00 + 0.50 = 2.40

    signed = 2.40 / 13 = 0.1846

Report:

    task_id              = "jsonplaceholder"
    ewcs                 = 0.4923
    signed_score         = 0.1846
    has_incorrect_layer  = True
    total_applicable_weight = 13
    positive_weight      = 6.40
    contributions        = (six LayerContribution objects)
    missing_layers       = ()

Note the signed score: 0.1846. An earlier draft of this document reported
-0.277 for the same example. That value did not match the contributions
shown. The corrected and verified value is 0.1846, enforced by
test_worked_example.


================================================================================
7. DESIGN DECISIONS AND RATIONALE
================================================================================

--------------------------------------------------------------------------------
7.1  One Result Per Layer
--------------------------------------------------------------------------------

Decision:

    The EWCS accepts exactly one LayerResult per verification layer.
    Attempting to record a second result for the same layer raises
    ValueError.

Rationale:

    There were three candidate designs:

    Design A: One LayerResult per layer. Each verifier aggregates its
              own per-claim results internally.

    Design B: Multiple LayerResults per layer. The EWCS aggregates
              them.

    Design C: The orchestrator aggregates before handing results to
              the EWCS.

    Design A was chosen for three reasons:

    1. Bounded formula. With one result per layer, the denominator is
       fixed at the sum of the applicable LAYER_WEIGHTS. The EWCS does
       not vary with how many claims happen to be extracted from the
       code. This matters for the experiment: two code samples that
       make the same number of API calls, one of which the extractor
       parses more thoroughly, must not receive different EWCS values
       for that reason alone.

    2. Clear ownership. Each verifier is the authority on its own
       layer. It evaluates all the claims it is responsible for and
       returns a single verdict. The EWCS is not in the business of
       deciding how to weight multiple results for the same layer.

    3. Simpler tests. The EWCS test suite exercises a fixed set of six
       inputs. There is no combinatorial explosion of "what if a layer
       returns three results, one of which is INCORRECT?"

    The verifier's aggregation policy (how it collapses multiple
    per-claim results into one layer result) is a separate design
    decision, owned by each layer class. It is documented in the layer
    documentation, not here.

--------------------------------------------------------------------------------
7.2  Canonical Weight Ownership
--------------------------------------------------------------------------------

Decision:

    LAYER_WEIGHTS in ewcs.py is the single authoritative source for
    layer weights. LayerResult.weight, if present, is validated against
    LAYER_WEIGHTS and rejected on mismatch.

Rationale:

    Two failure modes were considered:

    1. Silent drift. If the weight lives only in LayerResult and each
       verifier sets it independently, a copy-paste error in one layer
       changes the score invisibly. The score depends on the layer
       class, not on the research design.

    2. Schema churn. Removing weight from LayerResult forces every
       layer class to be edited as part of the EWCS work. That breaks
       the "one file per owner" split and blocks the EWCS from being
       finalised independently.

    The chosen design avoids both:

    - LAYER_WEIGHTS is authoritative. The score depends on this dict,
      not on any verifier.

    - LayerResult.weight is retained. Layer classes can declare their
      intended weight; the schema stays as-is.

    - record() validates. If a verifier reports a weight that disagrees
      with LAYER_WEIGHTS, record() raises ValueError. The disagreement
      is surfaced immediately, not silently absorbed.

    The validation uses getattr(result, "weight", canonical) so that if
    the field is later removed from the schema, record() still works
    and simply uses the canonical value.

    The consequence: LAYER_WEIGHTS must be the only place where weights
    are defined. Changing a weight means changing this dict, updating
    the sensitivity analysis, and re-running the tests. Nothing else.

--------------------------------------------------------------------------------
7.3  Immutable Report
--------------------------------------------------------------------------------

Decision:

    EWCSReport and LayerContribution are frozen dataclasses. Nested
    sequences are tuples, not lists.

Rationale:

    The report is the artefact the DecisionPolicy consumes and the
    ConfidentAgent surfaces. It is the basis of the experiment's
    measurement. Once computed, it must not change.

    A frozen dataclass prevents field reassignment:

        report.ewcs = 0.9   # TypeError

    But frozen does not reach into nested objects:

        report.contributions.append(...)  # would work if contributions
                                          # were a list

    So the report uses tuples. A tuple of frozen dataclasses is fully
    immutable. There is no way to change the report or any part of it
    after finalise() returns.

    Why this matters for the experiment:

    If the report were mutable, a downstream stage could inadvertently
    modify it (e.g., during logging or when marshalling to JSON). The
    same report could then present different values to different
    consumers. Immutability guarantees that all consumers see the same
    numbers.

    Frozen is not transitive, so the discipline extends: every nested
    type in the report is itself frozen or immutable.

--------------------------------------------------------------------------------
7.4  Thread Safety
--------------------------------------------------------------------------------

Decision:

    EWCS uses a threading.Lock to guard record() and finalise().

Rationale:

    The six verification layers are independent. In the current
    design they are called sequentially by the orchestrator, but this
    is not guaranteed. Two scenarios make concurrency plausible:

    1. Future parallelism. If the orchestrator ever runs layers in
       parallel to reduce latency, six threads will call record()
       concurrently.

    2. Defensive design. Even if parallelism is never enabled, thread
       safety is cheap and prevents a whole category of bugs if the
       tool is ever embedded in a multi-threaded host (e.g., a web
       service).

    What the lock protects:

    - The _results dict (concurrent writes would corrupt it)
    - The _finalised field (a race between finalise() and record()
      could leave the object in an inconsistent state)
    - The invariant "no record after finalise" (checked and enforced
      under the lock)

    What the lock does NOT protect:

    - The EWCSReport itself. The report is immutable, so no lock is
      needed to read it.
    - The task_id. Set once in __init__ and never modified.

    Why hold the lock during finalise's computation?

    The commentary noted this and it is a valid point: the lock is held
    while _compute() runs. _compute() is O(6) — six iterations, two
    sums, one dataclass construction. It is bounded by microseconds.
    Holding the lock for the entire computation is simpler than a
    check-then-release pattern and the cost is negligible.

    The alternative — release the lock, compute, reacquire, and check
    for a race — adds complexity for no measurable benefit. If the
    layer count grows to hundreds, this can be revisited. For six, it
    is fine.

    Why not use a more sophisticated concurrency primitive?

    Options considered:

    - threading.RLock: unnecessary. There is no re-entrancy.
    - asyncio.Lock: would require the API to be async, which imposes
      a design on every caller. The layers are synchronous.
    - No lock at all: unsafe if parallelism is ever introduced.
    - multiprocessing: the EWCS lives in one process.

    A plain threading.Lock is the right primitive for a synchronous,
    single-process accumulator with a bounded, fast critical section.

    Idempotence of finalise():

    finalise() is guarded by the same lock. On the first call, _finalised
    is None, so _compute() runs and populates it. On subsequent calls,
    _finalised is already set and is returned directly. This is safe
    under concurrency: two threads calling finalise() simultaneously
    serialise on the lock; the second sees the cached report.

    The idempotence contract has a specific test (test_finalise_idempotent)
    that asserts the object identity of the two returns is the same.

--------------------------------------------------------------------------------
7.5  Missing Layer Policy
--------------------------------------------------------------------------------

Decision:

    At finalise time, any expected layer that did not report is filled
    with a synthetic LayerResult:

        state              = UNVERIFIABLE
        tier               = NONE
        weight             = 0
        evidence_source    = "none"
        evidence_detail    = "Layer did not report"

    This filled result appears in the report's contributions with weight
    0, so it does not affect the denominator. The layer is also listed
    in EWCSReport.missing_layers.

Rationale:

    Three candidate policies were considered:

    Policy A: Treat a missing layer as an error. Refuse to finalise.

    Policy B: Treat a missing layer as UNVERIFIABLE with its normal
              weight. It counts against the score.

    Policy C: Treat a missing layer as weight 0. It does not count
              against the score, but it is flagged.

    Policy A was rejected because it makes the EWCS brittle. A single
    bug in one verifier would crash the entire verification pipeline
    for every task, including the ones it could have scored correctly.

    Policy B was rejected because it conflates two different kinds of
    failure:

        - "I checked and could not verify"    → UNVERIFIABLE, counts
        - "I did not run at all"              → system failure

    These are different failure modes. A system failure is a bug; a
    verification failure is a finding. Penalising the score for a bug
    would conflate the two and make the metric harder to interpret.

    Policy C was chosen:

        - The score is not diluted by a layer that did not run.
        - The gap is visible: missing_layers is non-empty.
        - A downstream consumer (or an evaluation script) can decide
          whether a partial-coverage task should be excluded from
          analysis.

    The report is honest about partial coverage without over-penalising
    the score.

    The design principle: the EWCS reports what it knows. If it does not
    know something (a layer did not run), it says so, and it does not
    pretend the missing evidence supports or undermines the code.

--------------------------------------------------------------------------------
7.6  Why No Configuration Options
--------------------------------------------------------------------------------

Decision:

    EWCS.__init__ takes only task_id. No tier factors, no weight
    overrides, no threshold parameters, no per-run configuration.

Rationale:

    An earlier draft allowed tier_factors and layer_weights to be
    passed to __init__, for sensitivity analysis. This was removed.

    Reasons:

    1. Single source of truth. If a caller could pass weights, there
       would be two places where weights are defined (the module
       constant and the caller's dict). Drift becomes possible.

    2. The sensitivity analysis belongs elsewhere. The five weighting
       schemes (A–E) are an experimental concern, not a per-call
       concern. They should be implemented as separate experiments
       that run the pipeline with different LAYER_WEIGHTS, not as
       arguments threaded through every EWCS construction.

    3. Boring is better. The EWCS has a small, fixed surface. Fewer
       configuration knobs means fewer ways to get the wrong answer.
       The commentary explicitly recommended this: "The EWCS should
       stay deliberately boring."

    If sensitivity analysis needs to vary weights, the correct approach
    is to modify LAYER_WEIGHTS (or to write a sibling module that
    computes EWCS with alternative weights) and to run the pipeline
    again. This keeps the production EWCS unchanged and makes the
    experimental variants explicitly separate.

--------------------------------------------------------------------------------
7.7  Why No Coverage Metric
--------------------------------------------------------------------------------

Decision:

    EWCS does not expose a coverage percentage. It exposes EWCS,
    signed_score, has_incorrect_layer, total_applicable_weight,
    positive_weight, contributions, and missing_layers. It does not
    expose a derived "coverage" value.

Rationale:

    Coverage was considered as a companion metric. It would be:

        coverage = number of layers that reported
                 / number of expected layers

    This was rejected for two reasons:

    1. missing_layers already communicates the same information. A
       caller that wants coverage can compute it in one line:

           coverage = (len(EXPECTED_LAYERS) - len(report.missing_layers)) \
                    / len(EXPECTED_LAYERS)

       There is no need to bake it into the report.

    2. A coverage metric is a policy concern, not a scoring concern.
       Whether coverage matters for a decision — whether a partial
       report should be delivered, flagged, or abstained on — is a
       decision the DecisionPolicy makes, not the EWCS. Adding
       coverage to EWCSReport would conflate the two.

    The current design gives the DecisionPolicy everything it needs to
    implement a coverage rule if the experiment shows it is useful.
    The EWCS does not pre-empt that decision.

    The same reasoning applies to any other metric proposed during
    review: it belongs in the policy layer or in the evaluation script,
    not in the EWCS. The EWCS produces the raw numbers.

9. FAILURE MODES AND EXCEPTIONS
================================================================================

The EWCS raises three exceptions:

ValueError — Duplicate layer

    Raised by record() when a LayerResult is recorded for a layer that
    already has a result.

    Trigger:
        ewcs.record(make(INTERFACE, CORRECT))
        ewcs.record(make(INTERFACE, CORRECT))  # ValueError

    Reason:
        Enforces the one-result-per-layer contract.

ValueError — Weight mismatch

    Raised by record() when result.weight disagrees with
    LAYER_WEIGHTS[result.layer].

    Trigger:
        ewcs.record(make(ACCESS_POINT, CORRECT, weight=99))

    Reason:
        Enforces LAYER_WEIGHTS as the authoritative source.

RuntimeError — Record after finalise

    Raised by record() when called after finalise() has been called.

    Trigger:
        ewcs.record(make(INTERFACE, CORRECT))
        ewcs.finalise()
        ewcs.record(make(IDENTIFIER, CORRECT))  # RuntimeError

    Reason:
        The report is immutable. Mutating the accumulator after
        computing it would allow the report and the accumulator to
        diverge.

No other exceptions are raised. In particular:

    - finalise() never raises. It fills missing layers and computes.
    - __init__ never raises beyond what Python itself raises for a
      missing argument.
    - is_complete never raises.

If a layer result has an unexpected tier (e.g., TIER_3, which is
reserved), _contribution handles it via DEFAULT_TIER_FACTORS.get(tier,
0.0). An unrecognised tier contributes a factor of 0. No exception.


================================================================================
10. INTEGRATION POINTS
================================================================================

The EWCS is used by three callers:

1. The LayerOrchestrator (verification/orchestrator.py)

   After dispatching to all six verifiers and collecting their
   LayerResult objects, the orchestrator:

       ewcs = EWCS(task_id=task_id)
       for result in layer_results:
           ewcs.record(result)
       report = ewcs.finalise()

   The orchestrator then hands the report to the DecisionPolicy.

   The orchestrator never inspects the report's internals. It passes
   it through.

2. The DecisionPolicy (scoring/decision.py)

   Consumes the report. Uses:

       report.has_incorrect_layer   for the safety constraint
       report.ewcs                  for the confidence thresholds

   Does not use:
       report.signed_score          (diagnostic only)
       report.contributions         (used in logging and in the report)
       report.missing_layers        (may be used if a coverage rule is
                                     added later)

3. The ConfidentAgent (verify.py)

   Constructs the VerificationReport returned to the caller. Copies:

       report.ewcs              → VerificationReport.ewcs
       report.signed_score      → VerificationReport.signed_score
       report.has_incorrect_layer
                                → VerificationReport.has_incorrect_layer
       report.missing_layers    → VerificationReport.missing_layers

   The VerificationReport does not embed the EWCSReport. It copies the
   fields it needs. This keeps schemas.py free of any dependency on
   the scoring subpackage.

The EWCS imports nothing from clients, extraction, or verification. It
depends only on schemas.py. This is the property that allows the EWCS
to be tested in isolation and to be reused with any set of layers that
produce LayerResult objects.


================================================================================
11. FROZEN CONTRACT SUMMARY
================================================================================

Everything in this section is frozen. Changing any of these requires
updating the tests, the documentation, and any downstream consumer.

    One LayerResult per layer.
        Enforced by ValueError on duplicate record.

    LAYER_WEIGHTS is authoritative.
        Enforced by ValueError on weight mismatch.

    Immutable report.
        EWCSReport and LayerContribution are frozen dataclasses.
        Nested sequences are tuples.

    Thread-safe.
        record() and finalise() are guarded by a threading.Lock.

    Idempotent finalise().
        Repeated calls return the same report object.

    No configuration.
        __init__ takes only task_id.

    Missing layers.
        Filled as UNVERIFIABLE with weight 0, listed in missing_layers.

    No coverage metric.
        Coverage is a policy concern, not a scoring concern.

    No mutation after finalise.
        Enforced by RuntimeError on record after finalise.

    Round to four decimal places.
        Both ewcs and signed_score are rounded to 4 places.

    No dependencies on other tool subpackages.
        EWCS imports only from schemas.py.
