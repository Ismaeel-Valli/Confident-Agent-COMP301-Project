2. PROJECT CONTEXT AND RESEARCH QUESTION
================================================================================

2.1 Origin

This project originates from the COMP301 Software Design brief on "Confident
Agents" - an investigation into how software engineers can design AI systems
that recognise the limits of their own knowledge before presenting information
to users.

The brief framed the challenge as:

    "A Confident Agent is not one that is always correct.
     It is one that knows when it should not be trusted."

This is a philosophy, not just a technical requirement. It reframes the goal of
AI safety from "eliminate errors" (impossible) to "recognise and communicate
uncertainty" (achievable).

2.2 Why This Matters

Large Language Models have transformed software development. Developers
increasingly use LLMs to generate code from natural language descriptions. But
LLMs hallucinate - they produce code that looks correct, is presented with
confidence, and is actually wrong.

For code generation specifically, hallucinations are particularly dangerous
because:

- Code executes. A wrong API call fails or does something unintended.
- Code is trusted. Developers copy-paste without verifying.
- Errors compound. A single wrong function call breaks the whole program.
- Documentation is fragmented. Verifying an API call requires checking multiple
  sources.

The specific problem we address is REST API hallucinations in generated code.

2.3 The Research Question

After extensive refinement, we settled on:

    "Can an LLM-based code-generation system use external static verification
     to reduce unacceptable REST API hallucinations reaching the user, while
     maintaining appropriate abstention behaviour when verification is
     inconclusive?"

Why this wording?

- "external static verification" -> We do not rely on the LLM to check itself.
  We use external sources (OpenAPI specs, Pyright) that are independent of the
  generating model.

- "reduce unacceptable REST API hallucinations" -> We do not claim to eliminate
  hallucinations. We measure reduction. "Unacceptable" means claims that violate
  the API specification. "REST API" scopes the project to a well-defined domain.

- "reaching the user" -> This is the actual harm we want to prevent. An
  incorrect claim that never reaches the user is not a failure.

- "appropriate abstention behaviour" -> The agent must know when to refuse to
  answer. This is the "confident" part - the agent recognises its own
  uncertainty.

- "when verification is inconclusive" -> Not all cases can be resolved. The
  agent must handle ambiguity.

2.4 The Scientific Hypothesis

Agent-based validation architectures equipped with explicit evidence-based
verification and abstention can significantly reduce unacceptable REST API
hallucinations compared with an equivalent baseline LLM operating without
validation.

Statistical significance will be assessed using McNemar's test for paired
binary outcomes at alpha = 0.05, with effect size and 95% confidence intervals
reported alongside p-values. The primary outcome is unacceptable API claims
reaching the user per prompt (binary: Yes/No).

2.5 The Confident Agent Philosophy

This philosophy guides the entire project:

    The agent does not need to be perfect - it needs to recognise the limits of
    its own knowledge and act accordingly.

The project investigates three capabilities:

1. Detection: Can the agent identify API hallucinations?
2. Correction: Can the agent fix identified hallucinations?
3. Abstention: Can the agent refuse to respond when verification is
   inconclusive?

3. CORE DEFINITIONS
================================================================================

3.1 What is a Hallucination?

Definition:

An LLM hallucination is content that appears plausible and confident but is
actually incorrect, fabricated, or unsupported by ground truth.

Key characteristics:

- Plausible: Looks correct to an untrained eye.
- Confident: Presented without hedging or uncertainty.
- Incorrect: Violates verified ground truth.

Example:

    import requests
    response = requests.get_json("https://api.github.com/users/octocat")
    # 'get_json' does not exist in the 'requests' library

3.2 What is an API?

Definition:

An API (Application Programming Interface) is any documented, programmatically
accessible interface - exposed by a language runtime, standard library,
third-party framework, operating system, or external web service - that can be
invoked by software to perform a specific operation.

Six conceptual layers:

Layer              Description
-----------------  ------------------------------------------------------------
Owner              Who publishes the interface
Access Mechanism   How it is invoked (import, HTTP verb)
Identifier Path    Fully qualified name (requests.get, /users/{id})
Input Contract     Expected parameters and types
Output Contract    Expected return value or response
Access Point       URL, module, or namespace

3.3 What is an API Hallucination?

Definition:

An API hallucination is a claim in generated code that is VERIFIED INCORRECT
against an authoritative ground-truth source.

The key insight: "Cannot be verified" does NOT equal "is false."

We distinguish four states:

State                Meaning                                  Agent Action
-------------------  ---------------------------------------  ----------------
VERIFIED_CORRECT     Evidence supports validity                DELIVER
VERIFIED_INCORRECT   Evidence contradicts validity             CORRECT or ABSTAIN
UNVERIFIABLE         Insufficient evidence                     ABSTAIN
NOT_APPLICABLE       Layer irrelevant to this task             Excluded

Critical distinction: NOT_APPLICABLE != UNVERIFIABLE. N/A is excluded from
scoring; UNVERIFIABLE counts against confidence.

3.4 The Hallucination Taxonomy (H01-H10)

ID    Type                             Layer
----  -------------------------------  --------------------------------
H00   No hallucination                 N/A
H01   wrong_endpoint                   Access Point
H02   wrong_http_method                Access Point
H03   nonexistent_parameter            Input Contract
H04   missing_required_parameter       Input Contract
H05   wrong_parameter_location         Input Contract
H06   wrong_parameter_type             Input Contract
H07   invalid_request_body             Input Contract
H08   missing_required_field           Input Contract
H09   invalid_header_or_authentication Contextual
H10   nonexistent_api_operation        Identifier

4. SCOPE DECISIONS AND JUSTIFICATION
================================================================================

4.1 Why Python Only?

Reason 1: Pyright - Pyright is a production-grade static analysis tool for
Python, maintained by Microsoft and released under the MIT licence. It is the
same analysis engine that powers Pylance, but it ships as a standalone
command-line tool with JSON output. This makes it directly invokable from our
pipeline via a subprocess call, without an IDE or LSP client. It is backed by
typeshed, the canonical Python type stub repository.

Reason 2: requests library - Python's requests library is the de facto standard
for making HTTP requests. It has a simple, uniform API.

Reason 3: OpenAPI ecosystem - The Python ecosystem has mature OpenAPI tooling.

Reason 4: Reproducibility - Python code is easier to reproduce, test, and
review.

4.2 Why REST APIs Only?

Reason 1: OpenAPI specifications - REST APIs are described by OpenAPI
specifications. These are machine-readable, authoritative, and widely available.

Reason 2: Clear verification target - A REST API claim is easy to verify: does
the endpoint exist? Is the method correct? Are the parameters valid?

Reason 3: Real-world relevance - REST APIs are the most common integration
point for LLM-generated code.

4.3 Why Static Verification Only?

Reason 1: Safety - We never execute the LLM-generated code. Our own verification
tooling (such as Pyright, PyPI metadata queries, and OpenAPI parsing) may
execute in isolated subprocesses to analyse the generated code as a text
artefact. The generated code itself is never run.

Reason 2: Reproducibility - Static analysis is deterministic. The same code
always produces the same result.

Reason 3: No cost, no network dependency - Static analysis works offline and
does not incur API costs.

Reason 1: Free and local.

Reason 3: Reproducible with fixed parameters.
Reason 4: OpenAI-compatible API.
Reason 5: Open-source and inspectable.

Our Master dataset is fixed and contains 1,000 REST API tasks in Python, each

- A natural language instruction
- A structured API specification (OpenAPI-derived)
- Ground truth code
- A test case

5.4 The Evaluation Dataset

Field                          Type      Purpose
-----------------------------  --------  ------------------------------------
task_id                        string    Unique identifier

The evaluation dataset contains only task_id and
natural_language_instruction. The language field is present in the Master

When the pipeline is extended to other languages, the language field will be

The separation is:

Master Dataset = WHAT IS CORRECT
Evaluation Dataset = WHETHER THE MODEL'S OUTPUT IS CORRECT

5.6 Why Neutral Prompts?

All prompts are written in neutral natural language. They do not contain:

- "Use requests.get()"
- "Make sure the endpoint is /users/{id}"
- "Avoid hallucinating"

They DO contain:

- "Write a Python function that fetches a user from the JSONPlaceholder API"

If we tell the model to "use requests.get()", we are testing whether the model
can follow instructions, not whether it can generate correct code. This was
found to contribute negatively during earlier draft datasets.

6. THE VERIFICATION ARCHITECTURE
================================================================================

6.1 The Six Verification Layers

Layer                         Question                                      Source                                      Confidence
----------------------------  --------------------------------------------  ------------------------------------------  -----------------
1. Interface Existence        Does the library/module exist?                PyPI metadata or runtime import check       HIGH
2. Identifier Existence       Does the method/function exist?               Pyright diagnostics (typeshed)              MEDIUM
3. Access Point (Endpoint)    Does the endpoint exist? Is the method allowed? OpenAPI specification                     HIGH
4. Input Contract (Parameters) Are parameters correct (name, location, type, required)? OpenAPI spec + typeshed           HIGH / MEDIUM
5. Output Contract (Response)  Are response fields accessed correctly?       OpenAPI response schema + Pyright diagnostics HIGH / MEDIUM
6. Contextual Validity        Is the API valid for this context?            Package metadata, platform detection, deprecation data HIGH

6.2 The Evidence Hierarchy

Tier                        Factor   Sources
--------------------------  -------  --------------------------------------------
Tier 1 - AUTHORITATIVE      1.00     Official OpenAPI specifications; official API documentation
Tier 2 - STRONG SUPPORTING  0.80     Official package registries (PyPI); type definitions (typeshed)
Tier 3 - EMPIRICAL          0.90     Empirical execution (reserved for future work; NOT used in this phase)
Tier 4 - SUPPORTING         0.50     Pyright diagnostics

Evidence tier is claim-dependent. Tier 3 is not universally weaker than Tier 2.

6.3 Verification Flow

1. Interface existence
   Does the library/module exist?
   Source: PyPI (package registry)
   Badge: w3

2. Identifier existence
   Does the method/function exist?
   Source: Pyright (typeshed-based static analysis)
   Badge: w3

3. Access point (endpoint)
   Does the endpoint exist? Is the method allowed?
   Source: OpenAPI specification
   Badge: w4

4. Input contract (parameters)
   Are name, location, type, required correct?
   Source: OpenAPI spec + typeshed
   Badge: w2

5. Output contract (response)
   Are response fields accessed correctly?
   Source: OpenAPI response schema + Pyright
   Badge: w1

6. Contextual validity
   Is the API valid for this context?
   Source: package metadata, deprecation data
   Badge: w2

Badge = layer weight in the EWCS formula (weights sum to 15).

6.4 Pyright

Pyright is a static analysis tool maintained by Microsoft and released under
the MIT licence. It is the same analysis engine that powers Pylance, but it
ships as a standalone command-line tool. Our pipeline invokes Pyright as a
subprocess and parses its JSON output. Pyright reads the generated code as text
and produces diagnostics - it does not execute the code. Its diagnostics are
treated as strong evidence but not definitive proof.

Reasons Pyright may fail to resolve a valid attribute:

- Dynamic attributes (__getattr__, __setattr__)
- Metaclasses and generated methods
- Runtime registration or plugins
- Incomplete or outdated type stubs
- Conditional imports or environment-specific code

Therefore, Pyright diagnostics are treated as strong evidence, not definitive
proof, and are assigned Tier 4 in the evidence hierarchy. Their lower tier
factor (0.50) reflects this.

6.5 Why Not Runtime Execution?

We do not execute the LLM-generated code. Our own verification tooling may
execute in isolated subprocesses. Reasons we do not run the generated code:

- Safety: Never execute untrusted code.
- Reproducibility: Same code always produces same result.
- Cost: No API charges.
- Determinism: No network variability.

The trade-off: we cannot catch every error. But for API hallucinations
specifically, static verification catches the vast majority.

6.6 Why Pyright, Not Pylance

Pylance is distributed as a closed-source extension for Visual Studio Code and
is licensed for use only within Microsoft products. To invoke it
programmatically, one must implement a Language Server Protocol client -
spawning the process, framing JSON-RPC messages, and parsing asynchronous
diagnostic notifications. This adds significant implementation complexity for a
research pipeline that must remain auditable and reproducible.

Pyright is the open-source engine behind Pylance, distributed under the MIT
licence. It ships as a standalone command-line tool that accepts a file path and
returns diagnostics as a JSON document. This makes it directly invokable from
our pipeline via a single subprocess call, with no LSP client, no JSON-RPC
framing, and no protocol negotiation.

The analysis results are identical: both use typeshed as the source of type
information and emit the same diagnostic rules (reportMissingImports,
reportAttributeAccessIssue, reportArgumentType, reportReturnType, and others).
Because the engine is the same, no analytical capability is lost by choosing
Pyright over Pylance.

We therefore use Pyright as the type-stub-based verification source for Layers 2
(Identifier Existence) and 5 (Output Contract), alongside PyPI metadata (Layer
1) and OpenAPI specifications (Layers 3 and 4).

6.7 The MCP Tool Attachment

The idea is to have The Confident Agent exposed as an MCP (Model Context
Protocol) tool, allowing it to attach to any MCP-compatible LLM.

7. THE CONFIDENCE METRIC (EWCS)
================================================================================

7.1 Terminology

Three concepts are explicitly separated:

Term                                Definition
----------------------------------  --------------------------------------------
Verification State                  Categorical result per claim
Evidence-Weighted Confidence Score  Primary metric [0, 1]
Signed Verification Score           Diagnostic metric [-1, 1]

Important distinction: Ground truth = the dataset specification (known correct
API usage). Verification state = the verifier's estimate of correctness.

The verifier's output is NOT ground truth. It is an estimate of correctness
relative to ground truth.

7.2 Why Not a Probability

The EWCS is NOT a probability. A score of 0.95 does not mean "95% probability
of being correct." It means "95% of applicable verification weight is supported
by positive evidence."

The Evidence-Weighted Confidence Score is an evidence-weighted measure of
verification strength, not a calibrated probability of correctness.

7.3 Layer Weights

Layer                                Weight
----------------------------------  ------
1. Interface Existence                  3
2. Identifier Existence                 3
3. Access Point (Endpoint)              4
4. Input Contract (Parameters)          2
5. Output Contract (Response)           1
6. Contextual Validity                  2
TOTAL                                  15

The weights are operational design choices, not empirically established
universal weights. Sensitivity analysis is planned.

7.4 Tier Factors

Tier                                Source                              Factor
----------------------------------  ----------------------------------  ------
Tier 1                              OpenAPI, official documentation      1.00
Tier 2                              Package registry, typeshed           0.80
Tier 3                              Empirical execution (reserved)       0.90
Tier 4                              Pyright diagnostics                  0.50
NONE                                No evidence                          0.00

7.5 The EWCS Formula

EWCS is the proportion of applicable verification weight supported by positive
evidence:

    EWCS = [ SUM (w_i * tier_factor_i) for layers where state = VERIFIED_CORRECT ]
           -----------------------------------------------------------------------
           [ SUM (w_i) for all applicable layers ]

Where EWCS lies in [0, 1], and:

- w_i = the layer weight (see Section 7.3)
- tier_factor_i = the evidence strength factor for that layer (see Section 7.4)

The numerator sums the weighted positive evidence.
The denominator sums the total applicable weight.

Interpretation:

- 1.00 -> All applicable weight supported by Tier 1 positive evidence
- 0.80 -> All applicable weight supported by Tier 2 positive evidence
- 0.50 -> Half of applicable weight supported
- 0.00 -> No positive evidence found

7.6 The Signed Verification Score (Diagnostic)

It should be noted that the EWCS only counts positive evidence. As a result, we
cannot distinguish between:

- A layer that is UNVERIFIABLE (we don't know)
- A layer that is VERIFIED INCORRECT (we know it's wrong)

This is where Signed Verification comes in. Signed Verification is a diagnostic
metric in the range [-1, 1] that captures both positive and contradictory
evidence across the six verification layers - a secondary internal confidence
metric used for analysis. The signed score distinguishes the above mentioned
cases by giving negative scores to incorrect layers.

Signed score lies in [-1, 1]:

    signed_score = [ SUM (w_i * s_i) for all applicable layers ]
                   -------------------------------------------------
                   [ SUM (w_i) for all applicable layers ]

Where s_i is the per-layer signed score:

- VERIFIED_CORRECT   -> +1.0 * tier_factor
- VERIFIED_INCORRECT -> -1.0 * tier_factor
- UNVERIFIABLE       -> 0.0
- NOT_APPLICABLE     -> excluded

The signed score is NOT reported in the primary results. It is a diagnostic
metric for internal analysis and debugging.

7.7 Worked Example

Task: Fetch a user by ID from JSONPlaceholder.

LLM generates (incorrect):

    response = requests.get(f"https://jsonplaceholder.typicode.com/user/{user_id}")

Note: /user/{user_id} is incorrect (correct is /users/{user_id}).

Layer              Weight  State       Tier Factor  Positive Weight
-----------------  ------  ----------  -----------  ---------------
1. Interface            3  CORRECT     2            0.80 -> 2.40
2. Identifier           3  CORRECT     2            0.80 -> 2.40
3. Access Point         4  INCORRECT   1            1.00 -> 0.00
4. Input Contract       2  CORRECT     1            1.00 -> 2.00
5. Output Contract      1  CORRECT     2            0.80 -> 0.80
6. Contextual           2  N/A         -            excluded

EWCS = (2.40 + 2.40 + 0.00 + 2.00 + 0.80) / (3 + 3 + 4 + 2 + 1)
     = 7.60 / 13
     = 0.585

Decision: Safety constraint fires (Layer 3 INCORRECT) -> CORRECT.

For the correct version of the code:

EWCS = (2.40 + 2.40 + 4.00 + 2.00 + 0.80) / 13
     = 11.60 / 13
     = 0.892

Decision: No incorrect claims; EWCS (0.892) >= 0.85 -> DELIVER.

Sensitivity schemes:

Scheme              Weights (L1-L6)      Thresholds (Deliver/Flag)
------------------  -------------------  --------------------------
A. Proposed         3, 3, 4, 2, 1, 2     0.85 / 0.60
B. Equal            1, 1, 1, 1, 1, 1     0.85 / 0.60
C. Endpoint-Heavy   2, 2, 6, 2, 1, 2     0.85 / 0.60
D. Strict Thresholds 3, 3, 4, 2, 1, 2    0.90 / 0.70
E. Lenient Thresholds 3, 3, 4, 2, 1, 2   0.80 / 0.50

If the intervention reduces hallucinations under all five schemes, the result is
robust.

7.8 Sensitivity Analysis (Planned)

Sensitivity analysis across the five schemes above is planned to test robustness
to weight and threshold choices.

================================================================================
8. THE DECISION POLICY
================================================================================

8.1 Three Components

The decision policy has three distinct components:

Component 1: Safety Constraint (independent of confidence)

    IF any layer is VERIFIED_INCORRECT:
        emit CORRECT (route to correction sub-loop)

Component 2: Confidence Thresholds

    ELSE IF EWCS >= 0.85
        emit DELIVER
    ELSE IF EWCS >= 0.60
        emit DELIVER_WITH_FLAG
    ELSE
        emit ABSTAIN

The safety constraint is NOT a confidence rule. It is a hard rule that fires
independently of EWCS. This ensures that a high-confidence code with a single
critical error is still caught.

8.2 Why the Safety Constraint Matters

In the incorrect JSONPlaceholder example, EWCS = 0.585. Without the safety
constraint, this would trigger ABSTAIN - the correct outcome, but for the wrong
reason.

The safety constraint ensures the decision is driven by the presence of a
critical error, not by the numeric score alone.

8.3 Decision Thresholds (Researcher-Defined)

Threshold              Value   Role
---------------------  ------  ------------------------------------
High confidence        0.85    Deliver without flag
Moderate confidence    0.60    Deliver with flag
Below moderate         <0.60   Abstain

Thresholds are researcher-defined. Sensitivity analysis is planned.

================================================================================
9. THE AGENT CONTROLLER
================================================================================

9.1 Correction Sub-Loop

Correction is NOT part of the decision function. It is orchestrated by the agent
controller.

Flow:

1. Receive candidate code
   Output from the code-generating LLM

2. Run six-layer verification
   PyPI, Pyright, OpenAPI spec

3. Compute EWCS & signed score
   Evidence-weighted confidence

4. Apply safety constraint
   Any layer VERIFIED_INCORRECT?

5. Emit decision
   Deliver / deliver with flag / correct / abstain

6. Correction loop (max 1 attempt)
   Rewrite, then feed back for re-verification

If step 4 finds no error: skip to step 5 without looping through step 6.

Maximum correction attempts: 1 (fixed to avoid sampling bias).

9.2 Why the Separation?

Property       Reason
-------------  ------------------------------------------------------------
Purity         The decision function has no side effects.
Testability    The decision logic can be tested in isolation.
Modularity     Correction logic can be swapped or extended.

9.3 Multi-Agent Reframing

To align with the brief's suggestion of a multi-agent architecture, the pipeline
can be reframed as cooperating agents:

- Chief agent
  Orchestrates the pipeline, logs every step

- Generation
  LLM writes code

- Verification
  Six-layer static check

- Decision
  EWCS + safety rule

- Correction
  Single rewrite attempt

Each sub-agent reports back to the chief agent; correction results are
re-checked by verification.

This satisfies the brief's suggestion of multi-agent design. The Chief Agent
receives generated code, dispatches it to the Verification Agent, receives the
verification report, applies the decision policy, and routes to either
Correction, Delivery, or Abstention.

10. THE EXPERIMENTAL METHODOLOGY
================================================================================

10.1 Experimental Design

We use a controlled experiment comparing two conditions:

BASELINE

- Raw LLM generates code from the natural language instruction.
- No verification.
- No correction.
- No abstention.
- Output: Generated code.

INTERVENTION

- LLM generates code, then the Confident Agent:
  1. Verifies the code statically
  2. Corrects it if incorrect (max 1 attempt)
  3. Abstains if verification is inconclusive
- Output: Verified code OR abstention

10.4 The Evaluation Pipeline

For each output (baseline and intervention):

1. Parse the generated code
2. Extract the API call
3. Compare against api_specification (OpenAPI)
4. Classify outcome:
   - Correct (matches OpenAPI spec)
   - Hallucination (violates spec, H01-H10)
   - Python Error (syntax or type error unrelated to API)
   - Ambiguous (cannot determine)
5. For hallucinations, record the specific H-code
6. For interventions, check if the agent detected/corrected the issue

11. EVALUATION METRICS
================================================================================

11.1 Primary Metric

UNSAFE DELIVERY RATE (UDR):

    UDR = Incorrect outputs delivered to the user / Total outputs

This directly measures the harm we want to prevent.

11.2 Secondary Metrics

Metric                   Definition
-----------------------  ------------------------------------------------
Coverage                 Delivered / Total
Abstention Rate          Abstained / Total
Selective Accuracy       Correct Delivered / Total Delivered
Correction Success Rate  Successful corrections / Attempts
Correction Regression    Correct -> Incorrect after intervention
EWCS Distribution        Mean/median EWCS (baseline vs intervention)
Precision                TP / (TP + FP)
Recall                   TP / (TP + FN)
F1 Score                 2 * (P * R) / (P + R)

11.3 The Four Evaluation Questions

Q1 - Does the LLM hallucinate?
     Measured by natural hallucination rate (baseline).
     Purpose: establishes the problem.

Q2 - Can the verifier detect hallucinations?
     Measured by Precision, Recall, F1.
     Purpose: evaluates verifier capability.

Q3 - Does the complete agent reduce bad outputs?
     Measured by Unsafe Delivery Rate (baseline vs intervention).
     Purpose: primary experimental result.

Q4 - Does it know when not to answer?
     Measured by Abstention Rate, Selective Accuracy, Coverage.
     Purpose: evaluates the Confident Agent philosophy.

Q5 - Does confidence improve?
     Measured by EWCS distribution (baseline vs intervention).
     Purpose: secondary quantitative metric.

11.4 Statistical Analysis

Statistical test         McNemar's test for paired binary outcomes
Primary outcome          Unacceptable API claims reaching the user per prompt (binary: Yes/No)
Significance level       alpha = 0.05
Effect size              Odds ratio or relative risk reduction with 95% CI
Multiple comparisons     Primary outcome designated; secondary outcomes reported as exploratory

The contingency table (McNemar's test compares cells b and c):

                     Intervention
Baseline        Correct        Wrong
Correct         a              b
Wrong           c              d

15. GLOSSARY
================================================================================

Term                          Definition
----------------------------  ------------------------------------------------------------
Abstention                    The agent's refusal to deliver code when verification is inconclusive.
Baseline                      The experimental condition where the raw LLM generates code without verification.
Confident Agent               An agent that recognises the limits of its own knowledge and abstains when verification is inconclusive.
Correction Loop               The process of feeding validation errors back to the LLM for a single rewrite attempt.
Evidence Hierarchy            The ranking of evidence sources by authority (Tier 1 = authoritative, Tier 4 = supporting).
EWCS (Evidence-Weighted
Confidence Score)             The primary confidence metric. Proportion of applicable weight supported by positive evidence. Range [0, 1]. Not a probability.
Ground Truth                  The correct API usage recorded in the dataset specification. Not the verifier's output.
H01-H10                       The ten REST-specific hallucination types.
JSONL                         JSON Lines - one JSON object per line.
McNemar's Test                A statistical test for paired binary outcomes.
MCP                           Model Context Protocol - a standard for LLM tool integration.
OpenAPI                       A specification standard for describing REST APIs.
Pyright                       Microsoft's open-source Python static type checker. Used as the type-stub-based verification source for Layers 2 and 5. Same engine as Pylance but invoked as a command-line tool.
Signed Verification Score     Diagnostic metric in [-1, 1]. Captures both positive and contradictory evidence. Not reported in primary results.
Four-State Verification Model The classification of API claims as VERIFIED_CORRECT, VERIFIED_INCORRECT, UNVERIFIABLE, or NOT_APPLICABLE.
Unsafe Delivery Rate (UDR)    The proportion of outputs that contain an incorrect API claim and are delivered to the user.
Verification State            The per-layer categorical result from the verifier. NOT ground truth - an estimate of correctness relative to ground truth.
