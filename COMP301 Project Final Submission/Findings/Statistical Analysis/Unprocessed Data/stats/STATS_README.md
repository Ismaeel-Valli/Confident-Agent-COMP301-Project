# Project statistics (data dictionary)

Generated by `Findings/EvaluateBenchmark/compile_stats.py` from the evaluator's results
(`../evaluation/<label>/per_task.jsonl`), the benchmark's per-task result files and run
manifests (the zipped runs in `Findings/Benchmark/Completed Runs/`), and the dataset. The
tables are regenerated from scratch each time; never edit them by hand. Rerun after every
new benchmark run:

```bat
cd Findings\EvaluateBenchmark
python evaluate_benchmark.py
python compile_stats.py
```

The findings use three main runs (Qwen3.5-9B at Q4_K_M, Q6_K and Q8_0), so
`preliminary/` is not created; it would hold a run made with an older benchmark version.

## Layout

```
stats/
  runs.csv                              one row per run: settings, machine, role, whole-run totals
  by_quantization/<quantization>/<label>/   the main runs, one folder per quantization level
  preliminary/<quantization>/<label>/       runs made with an older benchmark version
  combined/                             every run in one file per table
```

Each `<label>` folder (and `combined/`, with all runs stacked) has:

| File | Content |
|---|---|
| `prompt_stats.csv` | one row per prompt: every label and measure |
| `group_stats.csv` | one row per group (overall, API, operation category, HTTP method, difficulty, authentication, specification source): rates, repairs and regressions, cost |
| `metrics_long.csv` | the same numbers in tidy form, one measurement per row (below) |
| `verifier_detection.csv` | the verifier as a hallucination detector |
| `error_kinds.csv` | kinds of error reaching the user, per group |
| `run_info.json` | the run's settings, machine and headline figures (`by_quantization` and `preliminary` only) |

`combined/` also has `run_comparison.csv` (one row per run, every group_stats "overall"
figure) and `quantization_comparison.csv` (the main runs only, one row per quantization
and one column per headline measure: the table for comparing quantizations and models).

**Runs and roles.** A run is one model at one quantization, identified by its
`model_label`. Its **quantization is the one LM Studio reported** for the loaded model,
not the one in the label (`runs.csv` column `label_matches_quantization` flags a
disagreement). A run is **main** when it used the newest benchmark version found, and
**preliminary** when it used an older one (different measurements or verifier): it is
scored and kept but not part of the comparison. Holm's correction (plan §6) is applied
across the main runs only; a preliminary run keeps its uncorrected p-value
(`hallucination_mcnemar_p_holm` is empty). Column `run_role` in every table says which.

**Conventions.** `b_` = baseline, `i_` = intervention (Confident Agent). Rates are
shares from 0 to 1. Empty cells mean "not recorded" (for example energy in a run made
before power measurement) or "undetermined". Classes follow `Benchmark/EVALUATION_PLAN.md`
§2: `correct`, `A` (API hallucination), `B` (valid call, wrong for the task),
`runtime_failure`, `undetermined`, `no_code`; for the intervention also `nothing_shown`
(withheld). Summaries (`group_stats`, `metrics_long`, `verifier_detection`, `error_kinds`,
the comparisons) exclude the 10 pilot tasks (plan §6); `prompt_stats` has all.

## runs.csv

`model_label`, `quantization`, `role`, `role_reason`, `label_matches_quantization`,
`model` (the identifier the benchmark used), `architecture`, `context_length`, `thinking`,
`temperature`, `max_tokens`, `max_turns`, `seed`, `benchmark_version`,
`frozen_package_evidence`, `started_first`, `machine_cpu`, `machine_gpu`, `machine_ram_gb`,
`power_backend`, `power_idle_w`, `git_commits`, `prompts`, `prompts_summarised`, and the
whole-run totals over **every** prompt (pilot included) as actually run: `b_run_hours`,
`i_run_hours`, `b_run_energy_wh`, `i_run_energy_wh`, `b_run_tokens`, `i_run_tokens`.

## prompt_stats.csv: one row per prompt and run

**Run.** `model_label`, `run_role`, `model`, `quantization`, `architecture`,
`context_length`, `thinking`, `temperature`, `benchmark_version`, `machine_gpu`,
`machine_cpu`.

**Prompt.** `task_id`, `api`, `operation_category` (read, create, update, delete,
search_filter), `http_method`, `endpoint`, `difficulty` (the dataset's heuristic),
`auth_type` (none, bearer, api_key, oauth2), `spec_source` (official provider
specification or documentation-derived partial one), `operation_family` (related prompts
share one), `pilot` (1 = development task), `instruction_chars`.

**Baseline.** `b_class`; `b_hallucination` (1 = class A, empty = undetermined);
`b_correct`; `b_hallucination_kinds` (class A), `b_task_error_kinds` (class B) and
`b_runtime_failure_kind` (see error_kinds.csv); `b_reasons` (the evaluator's findings);
`b_has_code`; `b_finish_reason`; behaviour checks `b_returns_expected`,
`b_empty_response_ok`, `b_error_raises`.

**Intervention.** `i_decision` (the verifier's final decision), `i_delivered`,
`i_withheld` (abstained), `i_ewcs`, `i_first_decision`, `i_first_ewcs`, `i_code_shown`,
`i_unapproved_code_shown` (code in the reply that the tool did not approve),
`i_shown_class` (what reached the user), `i_hallucination_reaches_user`,
`i_correct_reaches_user`, `i_hallucination_kinds`, `i_task_error_kinds`,
`i_runtime_failure_kind`, `i_shown_reasons`, `i_final_class` and `i_first_class` (the
last and first verified candidates, shown or not), `i_verification_calls`,
`i_tool_failures`, `i_model_turns`, `i_first_had_contradiction`,
`i_correction_attempted`, `i_correction_allowed`, `i_correction_count`,
`i_correction_outcome` (first class -> final class), `i_final_reply_prompted`,
`i_reply_matches_report`, `i_protocol_note_count`, `i_protocol_notes`, and the behaviour
checks as for the baseline.

**Cost, per mode** (`b_` and `i_`): `_duration_s` (wall clock for the prompt),
`_model_s` and `_tool_s` (time in LM Studio and in verification), `_model_requests`,
`_prompt_tokens`, `_completion_tokens`, `_total_tokens`, `_completion_tokens_per_s`,
`_gpu_energy_j`, `_cpu_energy_j`, `_energy_j` (sum of the measured channels),
`_energy_wh`, `_energy_above_idle_j`, `_energy_source` (nvidia-smi or
LibreHardwareMonitor), `_started`, `_error`. Energy covers the GPU and, with
LibreHardwareMonitor, the CPU package; not memory, storage or power-supply losses.

**Paired.** `pair_hallucination`: `repair` (baseline hallucinated, intervention did
not), `regression` (the reverse), `both`, `neither`. `pair_correct`: `repair`
(intervention delivered correct code, baseline did not), `regression` (baseline was
correct, intervention was not, including correct code withheld), `both`, `neither`.
`verifier_outcome`: the verifier as a detector of a hallucinated final candidate, TP
(hallucination withheld), FN (hallucination delivered), FP (non-hallucination withheld),
TN (non-hallucination delivered). `time_ratio`, `energy_ratio` (intervention / baseline)
and `extra_tokens` (intervention - baseline).

## group_stats.csv: per run and group

`dimension` is `overall`, `api`, `operation_category`, `http_method`, `difficulty`,
`auth_type` or `spec_source`; `group` is its value; `n` prompts.

- `b_/i_hallucination_rate` over decided prompts, each with its Wilson 95% interval as
  two numeric columns, `..._ci_low` and `..._ci_high`. The same for `correct_...`.
- `hallucination_paired_n`, `_repairs`, `_regressions`, `_both`, `_neither`,
  `_improvement` ((repairs - regressions) / paired n; positive = the intervention is
  better) and `_mcnemar_p` (exact). The same for `correct_...`. Subgroup p-values are
  descriptive (no correction for the number of groups); the `overall` row also has
  `hallucination_mcnemar_p_holm`.
- `b_/i_B_count`, `_runtime_failure_count`, `_undetermined_count`.
- `i_abstention_rate`, `i_incorrect_acceptance` (hallucination shown), `i_incorrect_rejection`
  (correct final candidate withheld), `i_unapproved_code_shown`, `i_mean_ewcs`,
  `i_mean_verification_calls`, `i_tool_failures`, `i_corrections_attempted`,
  `i_correction_success_rate` (final candidate correct), `i_final_reply_prompted_rate`,
  `i_protocol_compliance_rate` (no protocol notes).
- `b_/i_behaviour_all_ok_rate`: all three behaviour checks met.
- Time: `_mean_duration_s`, `_median_duration_s`, `_mean_model_s`, `_mean_tool_s`,
  `_total_duration_h`.
- Tokens: `_mean_prompt_tokens`, `_mean_completion_tokens`, `_mean_total_tokens`,
  `_total_tokens`, `_mean_completion_tokens_per_s`.
- Energy and power: `_mean_energy_j`, `_mean_energy_above_idle_j`, `_total_energy_wh`,
  `_total_gpu_energy_wh`, `_total_cpu_energy_wh`, `_total_energy_above_idle_wh`,
  `_mean_power_w` (total energy / total time).
- Efficiency: `_seconds_per_correct_answer`, `_wh_per_correct_answer` (total cost /
  prompts with correct code reaching the user).

## metrics_long.csv: tidy form

One measurement per row, made from group_stats, for pivoting in pandas, R or a
spreadsheet: `model_label`, `quantization`, `run_role`, `benchmark_version`, `dimension`,
`group`, `mode` (`baseline`, `intervention` or `paired` for measures that compare the two),
`metric` (the column name without its `b_` / `i_` prefix), `value`. Example:
`pandas.read_csv(...).pivot_table(index="quantization", columns=["mode", "metric"], values="value")`
after filtering `dimension == "overall"`.

## verifier_detection.csv

The verifier judged as a detector (positive = the final candidate is wrong; predicted
positive = withheld), overall and per API, for two targets: `A` (hallucination) and
`A_or_B` (hallucination or wrong for the task). `TP`, `FP`, `FN`, `TN`, `precision`,
`recall`, `f1`, `false_positive_rate` (correct work withheld), `false_negative_rate`
(wrong work delivered), `specificity`, `accuracy`. Undetermined candidates are left out.

## error_kinds.csv

Kinds of error in the code reaching the user, per run, mode (`baseline`,
`intervention`), `error_class` and category (`dimension` and `group` as in
group_stats). `tasks` prompts with the kind, `group_tasks` prompts in the group,
`share_of_group`. A prompt can have several kinds of class A or B.

| error_class | Kinds |
|---|---|
| `A` (API hallucination; project description appendix A.2) | wrong host, version or base path; invented endpoint or method; invented parameter or body field; invalid value or structure; missing required part or credential; undocumented response field; non-existent requests API |
| `B` (valid call, not the task's) | different declared endpoint; method not acceptable for the task; omitted parameter the task specifies; different parameter value; omitted request body; unrequested request body; request body differs (fields or values); extra requests; credential missing or malformed (API requirement unknown); JSON body sent as form data; insecure scheme (http) |
| `runtime_failure` (no request made) | input used as the wrong type (e.g. credential string as a dict); reads an input the task does not provide; syntax error; makes no request; does not finish (timeout); blocked operation; undefined name; raises its own error before the request; wrong call or argument types |

Anything not matched is `other`. The kinds are read from the evaluator's findings with
fixed rules (`evaluate_benchmark.py`: `HALLUCINATION_TYPES`, `TASK_ERROR_TYPES`,
`RUNTIME_FAILURE_TYPES`).

## Notes

- The primary result of the project (with bootstrap intervals over tasks and operation
  families) is in `results/report.md`; these tables are its descriptive companion. Rates
  here are per mode over decided prompts, so they can differ slightly from the report's
  paired primary row, which drops a prompt when either mode is undetermined.
- Quantizations are compared descriptively (one sample per task and run); the plan does
  not test differences between runs unless tasks are repeated with several seeds.
- Undetermined candidates stay out of the rates until the manual review of plan §4 is
  entered in `reviews/reviews.csv` and the evaluator is rerun.
